安卓Fridahook学习

简介

Frida是一款强大的动态代码插桩工具，它允许你在程序运行时，向进程注入JavaScript代码，实现对内存，函数调用，参数，返回值的实时监控和修改。本文将简单介绍Frida的代码注入原理和一些常用的API，并用frida-labs的十二道题目进行演示和解释。
参考文章Frida学习笔记

原理篇

每个安卓App运行时都是一个独立的Linux进程，它有自己的内存空间，正常情况下进程之间是相互隔离的，而Frida这样的动态插桩工具就是用来打破这个隔离，把我们的代码注入到目标进程的地址空间中，进而实现读取程序数据，调用程序函数等效果。
frida-server 在root权限下对进程发起ptrace，把自己内嵌的 frida-agent.so (包含了 QuickJS 引擎和 Frida Gum 引擎的共享库)写到程序的地址空间里面，Js引擎可以在App内部跑，访问App里的任何内存都不需要跨进程系统调用。

三个组件

frida-tools

电脑上用pip install frida-tools进行安装的命令行工具集。它负责接收我们编写的Js脚本并发送到frida-server并显示脚本执行结果。
其使用命令包括:

frida-ps:列出设备上的进程列表。
frida-trace:跟踪函数调用。
frida-ls-devices:列出已连接的设备。

frida-server

这是一个需要root的可执行文件，在手机上运行，用于接收电脑发的指令并对目标App进程执行注入操作，过程为:
ptrace attach -> 把frida-agent.so写入App进程空间 -> 劫持目标线程到agent的入口

其副作用主要有:

o
Ptrace会留下TracePid痕迹。在Ptrace attach期间，TracePid字段会变成frida-server的Pid，注入完成后server通常会自动detach，如果程序有检查/proc/self/status的TracePid字段的反调试，则注入可能会失败;目标进程的/proc/self/maps 里会多出frida-agent.so内存段无法抹除。

o
在Native Inline Hook时，Frida要把Native的开头覆写为跳转指令，Gum引擎会先SIGSTOP暂停目标进程所有其他线程，等写完跳转再SIGCONT进行恢复，如果hook过多Native函数会造成卡顿。

frida-agent

这是 Frida 的核心。它运行在目标 App 的进程空间内，包含两个关键子系统：
第一个是 JavaScript 引擎。Frida 历史上默认用的是 Duktape（一个轻量级嵌入式 JS 引擎，体积小、启动快），V8（Chrome 和 Node.js 用的那个）作为可选高性能引擎一直存在；近年（16.x 起）默认引擎换成了 QuickJS——同样轻量但 ES2020 语法支持更完整。三个引擎可以通过 Script.runtime 切换，常规 Hook 用默认即可，只有在 Stalker 这类需要高频 JS 执行的场景才考虑切到 V8。你编写的所有 JS 脚本都在这个引擎里执行。因为 JS 引擎本身就在目标进程内部，所以你的脚本可以直接访问目标进程的内存和函数——这不是远程调用，而是真正的「同进程执行」。
第二个是 Gum 引擎 ——这是 Frida 的 Hook 核心。Gum 是 Frida 团队开发的一个跨平台插桩库，用 C 语言编写，支持 x86、x86_64、ARM、ARM64 等多种架构。Gum 提供了两套 Hook 机制，分别对应 Java 层和 Native 层的函数拦截。当你在 JS 脚本里写 Java.use(“SomeClass”).someMethod.implementation = … 时，背后就是 Gum 引擎在工作。

其中frida-tools和frida-server.so的主版本和副版本必须匹配才能正常运行。可通过frida –version来检查frida-tools的版本。

Java层的hook原理

安卓应用的Java/Kotlin代码运行在ART虚拟机上，ART内部为每个Java方法维护了一个叫ArtMethod的数据结构，
它主要记录了以下信息：

entry_point_from_quick_compiled_code_：函数指针，指向该方法经过 JIT（即时编译）或 AOT（预编译）后生成的本地机器码入口地址，对于还没有被编译的方法，这个指针指向解释器的入口，由解释器逐条执行 DEX 字节码。
entry_point_from_interpreter_：如果该方法尚未编译，则指向解释器入口，由解释器逐行执行代码。
access_flags_：方法的访问权限（public, private, static 等）。
dex_cache_resolved_methods_：指向该方法所调用的其他方法的缓存。
Frida Java hook就是修改了entry_point_from_quick_compiled_code_这个指针，让它指向Frida的trampoline(跳板)代码，这个跳板确保了JS回调(this.方法())能正确执行，同时不破坏原始方法的逻辑。

这也关乎Frida的几个重要API的原理:

o
Java.perform(function()):通过 JNI（Java Native Interface）的 JavaVM->AttachCurrentThread() 将当前线程（也就是 JS 引擎所在的线程）附加到 ART 虚拟机。这一步完成后，当前线程就拥有了一个 JNIEnv 指针——后续所有 Java API 调用都要通过这个指针来完成。在 ART VM 的上下文中执行你传入的 function。在这个回调内部，你可以安全地使用 Java.use()、Java.choose() 等所有 Java 相关的 Frida API。function 执行完毕后，线程会保持附加状态（不会 detach）。这意味着 Hook 回调在任何时刻被触发时都能正常工作。


o
Java.use(“类名”):通过 JNI 的 FindClass 查找这个类（注意 JNI 中用 / 而不是 . 作为包名分隔符，Frida 会自动转换），然后创建一个 JavaScript 代理对象（Wrapper），把这个类的所有方法和字段都映射到 JS 属性上。这也解释了为什么要在perform里面使用use，因为perform后才有了JNIEnv指针，而FindClass依赖JNIEnv这个指针。


o
方法名.implementation=function(){}:这一行触发了真正的 Hook：Gum 引擎找到方法对应的 ArtMethod 结构体，保存原始的 entry_point_from_quick_compiled_code_，然后把它替换为 Frida trampoline 的地址。

由此可知我们是以方法为单位进行hook，且难以修改方法内部逻辑。

Native层的hook原理

当我们需要Hook到Native函数时，Frida使用Inline Hook技术，修改了目标函数开头的几条机器码为跳转指令，跳到Frida的trampoline代码。原始的几条被覆盖的指令会被保存到trampoline代码中执行，最后在trampoline代码末尾跳转到原代码。
trampoline会保存CPU寄存器，调用我们的onEnter回调，将寄存器的值作为args数组给我们使用。
在原始函数执行完后，return之前，又会再次跳到trampoline代码，调用我们的onLeave回调。

Spawn和Attach的区别和选择

安卓应用的启动过程为:
fork(进程创建)->attachBaseContext(壳解密入口) → ContentProvider.onCreate(SDK早期初始化) → static{}(类静态初始化) → JNI_OnLoad(so的加载入口) → Application.onCreate → MainActivity → 稳定运行。
Spawn是在attachBaseContext之前进行hook，而Attach是在稳定运行之后。

Spawn模式的格式为:frida -U -f app名 -l frida.js
Attach模式的格式为:frida -U -n app名 -l frida.js / frida -U -p -l frida.js
